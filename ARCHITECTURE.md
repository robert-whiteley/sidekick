# Architecture

## Layers

| Layer              | Tech                                                                                                                               | Why                                                                                               |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| UI + orchestration | Expo (React Native, new architecture, Expo Router, CNG + config plugins)                                                           | One UI codebase; iOS builds from Linux via EAS; maintained bindings for every engine below        |
| Always-on audio    | Local Expo module `modules/sidekick-native` (Kotlin, then Swift) running a foreground service with sherpa-onnx; emits events to JS | Wake word, VAD and transcription must keep running with the screen off and without JS overhead    |
| LLM / vision       | Google LiteRT-LM 0.20.0 with Gemma 4 E2B (`.litertlm`) — ADR 4, 10                                                                 | Uses each phone's fastest hardware (Tensor NPU, GPU, CPU fallback); Google-maintained; Apache-2.0 |
| Speech             | sherpa-onnx: Silero VAD v6, keyword spotter, Parakeet TDT 0.6B STT, 3D-Speaker embeddings, offline diarization                     | One Apache-2.0 runtime for all speech tasks; open-vocabulary wake word with no training           |
| Voice out          | System TTS (`expo-speech`)                                                                                                         | Zero download, fast on old phones. Later: Kitten / Piper via sherpa-onnx                          |
| Memory             | `@op-engineering/op-sqlite` with SQLCipher + sqlite-vec; EmbeddingGemma 2 text+vision embeddings                                   | Encrypted, fast, vector search in the same DB. USearch (HNSW) later for millions of vectors       |
| Camera             | `expo-camera`                                                                                                                      | Photo capture is all the MVP needs; vision-camera later if live frame processing is added         |
| Places             | GeoNames cities500 (offline, towns and villages) + learned places (home/work from dwell time)                                      | Place names with no network                                                                       |

## UI

One design for Android and iOS, the common ground of Material 3 and Apple's guidelines, identical on both (no platform ripple, native Switch or system Alert). Every screen builds from the component library in `src/ui` (rows, switches, sliders, bottom-sheet pickers with a tick, buttons, tabs, dialogs) and one token file, `src/ui/tokens.ts` (light/dark colours, a 4-pt spacing grid, type scale, 48-pt touch targets). `__tests__/ui-conventions-test.ts` is silent until a file in `src/app` or `src/features` imports a raw touchable, Switch, Text or TextInput from react-native, hard-codes a colour or font size, or uses spacing off the grid. The fix is to use or add a `src/ui` component or token, or to mark the line `// ui-exception: <why>` (or the file, in its first 10 lines, `// ui-exception-file: <why>`); an exception without a reason still fails.

Chat answers render through `src/ui/Markdown.tsx` (an own ~150-line parser, `markdown-logic.ts`: paragraphs, headings, bullet and numbered lists, bold / italic, small tables; no dependency), in the screen's light or dark colours. Read-aloud strips the same marks (`sentences.ts forSpeech`: bullets, `**`, table pipes). Edit / Try again (`chat-logic.ts lastExchange`, `assistant.ts forgetLastExchange`) take back only the last exchange: its turn leaves the saved chat state, its memory row is deleted, and the model's chat restarts from the running summary and the turns left (`Conversation.dropLast`), so the old answer is never seen again. The "How Sidekick answers" text is appended to the chat's system prompt (`prompts.ts withAnswerStyle`); changing it restarts the model's chat the same way. A question that will be read out is marked "(spoken)" in its prompt line so that answer stays plain. Messages sent while an answer is being written (typed, held mic, wake word, headset button) wait in a queue (`send-queue.ts`, pure), shown as faded bubbles with Send now / Edit / Remove, and are answered one at a time with the whole chat as context; one being edited waits. Stop and Send now end the answer through `llm.ts stopAnswer`: the running model pass ends with what it wrote (kept, marked "Stopped", in the chat and the model's history), and every later model step of that answer (routing, filling a tool, the lookup's second pass) returns nothing at once, so no tool runs after Stop; research and pictures stop through their own stop calls and nothing half-done is saved. Stopped before a word, nothing is kept (the model's chat restarts from the kept turns if it had seen the question), and with Send now that question is asked together with the new one. Talking over a spoken answer (barge-in) is Send now by voice.

## Memory model

- Store snapshots, audio and transcripts long-term; full video only for the recent past (years of video is ~10 GB/day — not feasible).
- Estimated ~1.6 M frame vectors per year (1 per 10 s × 12 h/day) ≈ 300 MB/yr at 256-dim int8.
- Recall: hybrid search (text vectors + photo vectors + keyword) → pick the moment → re-read the original image with the VLM for detail questions.
- Photos: EmbeddingGemma 2 Text Vision 440M puts text and images in one space. Each saved photo gets a vector of the image itself (`photos_vec`, shrunk to 512 px) in the same catch-up as text (`embedPending`, which every question runs first), so "the parking sign" finds the photo before the chat model has read it. The idle text reading still runs: exact numbers and words come only from that. Only the top 3 photo matches join the ranking (every photo is nearest to something). The vision encoder loads on the first photo, not with the text model.
- Deleting: sqlite-vec never frees or reuses a deleted vector's slot (its bytes stay in the file), and the word index keeps deleted words until merged. `src/memory/reclaim.ts` runs after deletes (and once per run when idle): it rebuilds a vector table once 1,024 slots are dead, merges the word index and VACUUMs when at least 1 MB and a tenth of the file is free; `secure_delete` zeroes freed pages. Measured on a copy with sqlite-vec 0.1.6: 1,228 memories plus 5,000 deleted ones took 7.3 MB before, 2.1 MB after, with none of the deleted vectors left in the file.
- Photo text: PaddleOCR PP-OCRv6 small (detection + recognition, ONNX) reads each photo when it is saved (~0.3–1 s on a laptop CPU, vs ~30 s for the chat model on a Pixel 5) and adds a `Read: "..."` line to the moment, so its words are searchable at once and by meaning after the next embedding pass. It runs on the `libonnxruntime.so` sherpa-onnx already ships, through a small JNI bridge (`modules/sidekick-native/android/src/main/cpp/ort_shim.cpp`). Photo questions also get the OCR text in the prompt so the model copies exact numbers. The idle chat-model reading now only runs on photos where OCR found no text.
- Private facts: unless Settings allows them, the owner-fact prompt tells the model to leave out health, religion or beliefs, sexuality, politics and money; facts other people say about themselves are stored with `facts.checked = 0` (hidden) until the idle fact pass asks the model which of them touch those topics: those rows are deleted, the rest are shown as suggestions. An unclear reply counts as private.
- Follow-ups (`followups` table): while idle and only if the chat model is already loaded, `followup-inference.ts` reads recent lines (last 2 days: speech, questions, photo notes) and proposes to-dos, events and reminders as `suggested`. Times are parsed in code (`followup-logic.ts`, relative to when each line was said), not by the model. Dismissed rows are kept so the same proposal isn't made again. Approved reminders and the optional morning digest are local notifications (expo-notifications, no push); the schedule is rebuilt from the table after every change. Events reach the phone calendar only via the OS "new event" screen (no calendar permission). "What do I need to do?" adds the approved follow-ups to the prompt.

## Memory budget

On phones under 6 GB RAM (iPhone 13 mini), and on any phone while Android reports low memory, the LLM and the embedder are never resident together: embedding unloads the LLM first, loading the LLM unloads the embedder, and live-camera frames wait (`Residency` in `Embedder.kt`). The iOS build uses the `increased-memory-limit` entitlement.

Memory pressure (`MemoryWatch.kt`, process-wide, so also with only the listen service running): Android's `onTrimMemory` running-moderate/low, and the low-memory flag (checked every 30 s while both models are loaded), unload the embedder; running-critical, background-list levels and `onLowMemory` unload both, the chat model only when no answer is being written. OCR goes too. JS drops its place-name pack (`memory-pressure.ts`); on iPhone a memory warning frees the embedder and the idle chat model from JS. Everything reloads on demand; a question that lands just after an unload loads the model and is asked again once.

The chip is chosen by measurement, not by a list: the first run times every backend that loads (one-token check, then a fixed prompt) and saves the fastest. On the Pixel 5 the GPU loads but writes slower than the CPU (2.9 vs 5.0 tokens/s), so it picks CPU. Measured on Pixel 5: typed question with memory ≈6 s, photo question ≈30 s.

## Listening

- A foreground service (Android, microphone type, permanent notification) owns one microphone loop shared by background listening and hold-to-talk.
- Per 32 ms chunk, on the mic thread (urgent-audio priority): wake-word spotter + Silero VAD. Each speech segment goes to one worker thread (bounded queue of 8; oldest dropped if it ever falls that far behind): transcribed (Parakeet; segments < 0.4 s or below -80 dBFS skipped), then voiceprinted (CAM++) only if ≥ 1.5 s or a short "yes"-type reply (consent needs its voice).
- Results go to an append-only journal file; the app drains it into the encrypted database when it is open. While the app is not on screen, the service answers wake-word questions itself (same model, same prompt) and speaks with the system voice.
- Places: when location is allowed, the service also gets the `location` type and Android's `LocationManager` (network/GPS/passive, every 5 min or 100 m) supplies a fix; each journal entry gets lat/lon if the fix is under 2 h old. JS names the place from the bundled GeoNames table (nearest town ≤ 30 km, preferring the most populous within 5 km) and stores it on the moment; the name is in the embedded text and the prompt.
- Auto-pause: quiet hours and "pause here" places (150 m + fix accuracy) are checked every 10 s; while paused, the wake word and conversation capture stop (push-to-talk still works) and the notification says why. Pausing in silence needs no setting: the VAD gate already skips all speech processing when nobody is talking.
- Conversation: answers are spoken natively (`Voice.kt`): Kyutai Pocket TTS via sherpa-onnx, sentence by sentence into an `AudioTrack` while each is generated; the system voice speaks until the optional voice download (98 MB, Wi-Fi only) is in, or if the first sound of a short sentence takes > 2.5 s. While Sidekick speaks and for 8 s after, the mic stays on (also with background listening off) and what the user says is the next question without the wake word; the chat history is kept (`keepHistory`). During this the mic switches to the call input with Android's `AcousticEchoCanceler`. Barge-in: a second Silero VAD at a stricter 0.7 threshold ducks the voice on the first speech chunk and stops voice + answer after 300 ms of speech; segments that end while Sidekick is still talking, and transcripts that mostly repeat what it just said, are dropped as echo. Logic: `Turns.kt` (JVM-tested).
- Consent mode (default on everywhere): other people's speech is kept only after the owner asks for consent and that voice says yes within 30 s. The owner's voice is learned from hold-to-talk and wake-word questions. A voice is written to the database only together with a kept line of theirs: until a voice agrees it lives in memory (`unsaved-voices.ts`: negative id, "Person N" on screen, learned in memory, forgotten after 10 min unheard or when the app closes), so speakers are still told apart live; when it says yes it is stored under the same label. At start, in consent mode, stored voiceprints of people who never agreed and have no kept line are removed (older builds stored one per voice); a person the user named or wrote notes about keeps their page without a voiceprint.
- Matching uses conversation context: a voice with at most 3 clips heard in the last 10 minutes (one still being learned) is joined from 0.45 instead of 0.55, and wins over an older voice unless that one scores 0.1 more (`matchSpeaker` in `voices.ts`). Never loosened for the owner.
- Live transcript: each `onTranscript` event (one per transcribed segment) makes the app drain the journal at once, so the phrase is assigned to a voice and shown on the Ask screen within ~1 s (`src/engine/live-transcript.ts`, in memory only). Lines from voices that haven't consented are shown greyed and marked "not saved" (on screen only, never stored); lines that weren't journaled (recording off) are shown with no speaker after 1.5 s. "Show conversation" only hides the panel; it doesn't change what is kept.
- People: every new voice gets a stable "Person N" label (`speakers.label_no`). A strong self-introduction ("my name is Sam", "hi, I'm Sam") names the voice automatically (`name_auto = 1`, Keep/Undo on the person page; Undo bans that name for the voice); weaker cues add evidence per voice (`speakers.suggested_count`): "Sam, can you…" points at the voice that answers next, "thanks, Sam" at the one that just spoke, and a live background Gemma pass over the conversation going on, run after each new line (`src/engine/name-inference.ts`), counts double; at 3 the name is applied as an auto name, below that it is an "Is this Sam?" suggestion. The same pass sets `speakers.description` ("Waiter") for unnamed voices, shown instead of "Person N". Renames are by speaker id, so they show everywhere. Owner lines like "Sam, can you send the report by Friday" become suggested to-dos linked to Sam (`followups.person_id`); things others say about themselves ("I live in Leeds") become suggested facts on their page (`facts.speaker_id`, kept out of the owner's facts). A question naming a person adds their notes, kept facts and requests to the prompt (`src/memory/people.ts`).
- Instructions only (Ask screen quick toggle, also in Settings): the mic loop transcribes a segment only right after the wake word, in a spoken follow-up, or for push-to-talk; ambient speech is dropped before transcription and nothing ambient is journaled. The wake word accepts the phrase with and without its greeting ("Hey Sidekick" and "Sidekick").

## Storage short

One rule on both sides (`storage-guard.ts`, `StorageGuard.kt`). Under the reserve (Settings → Storage): video, full-size camera stills and conversation audio pause (the words are still saved), and a model download that would go under the reserve is refused with how much to free. Under the floor (500 MB or 1% of the phone, at most the reserve) nothing big is written: no photos (the user sees "Phone storage is full"), keyframes, audio, downloads (one running is stopped), vectors, imports or new memories. Heard lines stay in the listener's journal file and frames in the camera's queue until there is space, so the database always has room for its own writes and is never left half-written.

## Interpreter

`src/engine/interpreter.ts` (session, in memory only), `interpreter-logic.ts` (languages, prompts, reply parsing; pure), screen `src/features/interpreter`, route `/interpret`. The model starts it: the router's `translate` tool with `talk: true` and the language the model named (one tool for both; as a tool of its own the sorter picked plain translate for 3 of 5 conversation requests).

- Turn: the side's mic opens (hold-to-talk path without partial transcripts), its tap ends the turn and returns the text. Android: the owner's English goes through the usual speech model; the other language through Parakeet v3 (the 25 European languages; reused when Listen already runs v3) or Whisper small (others), loaded on demand by `Interpreter.kt` and freed when the session ends. iPhone: Apple's on-device speech in that locale (`Speech.swift`), or a note that this iPhone can't hear it offline.
- Translation: one Gemma call per turn (throwaway chat, last 2 turns as context, streamed onto the other side; Pixel 5: ~5.3 s a turn, first words after ~3.2 s). On the owner's turns the same reply starts with `SIDEKICK: NO / END / LANGUAGE: <language>`: whether the line was an instruction to Sidekick rather than said to the other person. No word list; a missing or unreadable line translates as normal, and a translation isn't shown while the line says END or LANGUAGE. An END gets a second look, a short call asking only "who is this said to? OTHER / END / LANGUAGE" (`endCheckPrompt`, ~3.3 s, only on those lines): only END there ends the session, so a goodbye to the other person is still translated.
- Speaking: expo-speech with the language's tag (the phone's own TTS). Android checks the voice natively (`InterpretVoices`: ready / not downloaded / none) and can open the voice download screen; iPhone lists its voices.
- Models: Whisper small (375 MB, three files pinned to one Hugging Face commit) and Parakeet v3 (487 MB) download the first time a language needs them (Wi-Fi on its own; mobile data after the owner taps Download), then are kept (`settings.interpreterLanguages`; language.ts no longer deletes v3 while the interpreter uses it). Memory: Gemma plus one speech model, the same as Listen; the embedder isn't used.

## Data sources

Notes, picked folders, calendar and notifications become ordinary moments (kinds `note`, `file`, `event`, `notification`) in the encrypted database, so search and idle embedding treat them like anything heard. Imported moments carry `source_key` + `source_ver`; each re-scan (folders every 15 min, calendar every 6 h, contacts daily, while the app is open) diffs keys and versions, updating in place, adding or deleting (`src/memory/sources-logic.ts`). Text files are split into ≤1200-character passages. PDFs (Android) are read a page at a time by the native module: embedded text from Android's own PDF engine where the phone has the API, else the page is rendered and OCR'd; first 30 pages, chunked like text files (ADR 6). Contacts live in their own `contacts` table: they answer "what's X's number" with no model and turn a heard first name into a full contact name. Android notifications come from a `NotificationListenerService` in the native module that appends to an app-private file, drained into the database like the listening journal.

**Share in and attach** (`src/engine/share-in.ts`, `shared-doc.ts`, `shared-doc-logic.ts`): the share target (`plugins/with-share-target.js`: any type) hands `PhoneExtras.noteIntent` the intent; files are copied into `cache/shared` (≤ 400 MB, cleaned after 2 days) and the chat gets an attachment above the composer. The composer's paperclip (`File.pickFileAsync`, both phones) copies a picked file into `cache/attached` and goes the same way. Files are read by `src/files/` (below); PDFs use the folder-source reader (embedded text, else OCR); copies are deleted from the cache once read. Up to 9,000 characters are answered in one model pass; longer text is cut into 8,000-character parts (at most 24), each part gives short notes, and the answer is written from the notes. Recordings run in `Recordings.kt` on a background thread inside a `dataSync` foreground service with a progress notification: MediaExtractor/MediaCodec decode → 16 kHz → the same VAD, Whisper and voiceprint as Listen; lines go to an app-private JSONL file with a resume point, so a killed job carries on from where it was. Speakers are labelled within the recording with the Listen voice rules (`labelSpeakers`: "You" from the owner's voice, then "Speaker 1, 2…"); nothing becomes a person. The transcript is saved as `file` moments (`source_key` `shared:<id>`) unless Off the record, and the audio copy is deleted. A video's sound track goes through the same job (MediaExtractor takes its audio track); `videoFrames` (Kotlin `VideoFrames.kt` / Swift `VideoFrames.swift`) takes 4 still pictures, which the chat model describes on the first question.

**File readers** (`src/files/`, pure TypeScript, tested with made-up files): `read.ts` picks the reader from the first bytes and the name, reading through a `ByteSource` (`device.ts`: an expo-file-system file handle read in pieces, so big files never sit in memory whole). `zip.ts` (central directory, streaming fflate inflate with a cap), `office.ts` (.docx, .pptx with notes, .odt/.odp, EPUB spine), `workbooks.ts` (.xlsx shared strings, date styles, cached formula results; .ods), `xls.ts` (compound file + BIFF8), `sheet.ts` (cells, CSV with delimiter / decimal-comma / date detection, sheet summary), `text-formats.ts` (HTML, RTF), `kinds.ts` (types, magic bytes, plain descriptions of the rest). Spreadsheet questions: `src/engine/sheet-query.ts` asks the model for one Excel formula (`SHEET_TOOL`, the sheet's summary in its description), `formula.ts` works it out (tokenizer, parser, sandboxed evaluator with step / time / cell / depth limits; exact decimal sums), one retry with the error; "add a column" returns a changed sheet, saved as CSV through the share sheet. Folder sources read the same document types (`indexableKind` → `doc`).
**Pasted tables** (`shared-doc-logic.ts` `pastedTable`, `shared-doc.ts` `answerPastedTable`): three or more tab-separated lines in a question (cells copied from a spreadsheet or web page) are read as a sheet and the words around them as the question, answered like an attached spreadsheet (a formula worked out in code, so totals are exact).
**Follow-up replies** (`decide-logic.ts` `decidePrompt`): within the chat's 10-minute window the sorter sees the last exchange (clipped) before the request, so "yes" to "I can look that up" is sorted as a lookup.
**Web pages** (`src/web/page.ts`, `page-logic.ts`): a question holding a link, with Online on, fetches only that address (no cookies, public addresses only, 12 s, ≤ 3 MB) and keeps the main text with Sidekick's own readability-style extraction (drop scripts, menus, headers, footers, footnote marks and hidden parts; keep headings, paragraphs and list items that are not mostly links; prefer `<article>`, then `<main>`). Offline the question goes in the online queue (kind `page`, kept 3 days) and is answered when Sidekick is back online or Online is switched on.
**Text tools** (`ProcessTextActivity.kt`): `PROCESS_TEXT` opens a translucent trampoline that starts the main activity with the selection; the main activity is `singleTask`, so the result can't come from it directly. "Replace in the app" calls `finishProcessText`, which sets the trampoline's result and closes it, returning to the app. The selection result is never saved to memory.
**What did I miss?** (`src/engine/missed.ts`): the unread notifications from the listener, grouped by app and person (≤ 12 groups, 160 characters each), summarised by the model in 2–4 sentences; a plain count if the model can't run. It is a router tool (`missed`) and only reads.
**Waiting for the internet** (`src/engine/online-queue.ts`, `online-queue-logic.ts`): what needs the internet while there is none waits in a small list on the phone (encrypted key-value store, ≤ 20 items) and runs once back online, also with the app closed on Android (WorkManager with a network constraint, a 15-minute check and a live network callback, `Offline.kt`, waking the `SidekickRoutine` headless task). Kinds: an online lookup, the weather (kept 6 h), a pasted link, research (kept 3 days each) and directions (kept 3 h). Each item has a chat card with Cancel (shown again after a restart). Answers arrive as a card, in the chat history and as a notification when Sidekick isn't on screen. Directions split: a place known offline (a named place, home, a town in the GeoNames list) goes to Maps at once as coordinates, which navigates with offline maps; anything else waits, with "Open Maps now" on its card in case Maps' offline maps have it. Back online, Maps finds the place itself; Android 10+ doesn't let a background app open another app, so directions start by themselves only if asked for within 15 minutes and Sidekick is on screen, otherwise a card and a notification ("Directions to … are ready") wait for a tap. What each catalog tool needs from the internet is listed in `TOOL_NET` (offline / hands over to an app / partly / waits), checked against the catalog by `__tests__/online-queue-test.ts`. Emails wait in the outbox; model downloads in Android's download manager. iPhone: no background wake-up, so the list runs while Sidekick is open (network listener, and when it comes to the front).

## Research and photo edits

- Research (`src/web/research.ts`, pure parts in `research-logic.ts`): the router's `research` tool hands the topic over; one scratch-chat pass plans ≤ 4 search phrases (falls back to the topic's own words), each runs through `searchWeb` plus a Wikipedia full-text search, then up to 6 pages are read 3 at a time (https only, HTML only, ≤ 1.5 MB, 6 s each, no cookies). Wikipedia articles come as plain text from the API; other pages are reduced to their paragraphs. Pages are split into ~420-character passages, scored against the topic, off-topic pages dropped, and the best passages (≤ 4,400 characters) go into one report prompt with numbered sources; citations outside the list are removed. Requests send a User-Agent with the app's name only. Wikimedia allows such clients 10 requests a minute, so all Wikimedia requests (lookup and research) share one window of 9 a minute (`rate-limit.ts`); research trims its searches and reads fewer Wikipedia pages to fit (search snippets for the rest), and a 429 / Retry-After gets one wait-and-retry.
- Photo edits (`src/engine/photo-edit.ts`, `PhotoEdit.kt`): a photo sent with words that might be an edit gets one scratch-chat pass with only the `edit_photo` tool; the model replies with an edit or "none" (then the normal photo answer runs). Rotate, flip, crop, black and white and enhance (levels between the 0.5th and 99.5th percentile, a little saturation) are plain bitmap work; background edits run U²-Netp (320 px, ONNX through the OCR bridge) for a person/object mask with a soft edge, then remove (PNG), fill or blur (1/8-size box blur). Output ≤ 2048 px in app storage, deleted after 2 days unless saved.
- Erase and upscale (same files; `erase` and `upscale` ops of `edit_photo`, offered only with a photo): "erase" answers with a button to the brush screen (`src/app/erase.tsx`, geometry in `src/features/erase/erase-logic.ts`); the strokes (0..1 of the photo) become a mask and MI-GAN (28 MB, uint8 image + mask in, ONNX through the same bridge) fills it. "upscale" runs Real-ESRGAN general x4v3 (5 MB) in 128 px tiles with a 10 px margin, only for photos with a long edge ≤ 1024 px. Both models download the first time they are needed.
- Pictures (`src/engine/picture.ts`, pure parts in `picture-logic.ts`, `ImageGen.kt`, `cpp/sd_jni.cpp`): the `make_picture` catalog tool (offered only once the model is downloaded, decide.ts) hands over the description; a scratch-chat yes/no check by the model refuses sexual or nude pictures and minors in a sexual context, failing closed (the one thing Google Play requires blocking, ADR 0006); stable-diffusion.cpp (built from source, pinned, in `libsidekick_sd.so`) runs SDXS-512 (8-bit GGUF, 1 step, TAESD decoder) at 512×512 with progress events and a cancel flag. Optional 0.7 GB download from Settings → Assistant → Make pictures (terms in `docs/picture-terms.md`); Gemma and the embedder are unloaded first on phones under 7 GB, and the picture model unloads itself after a minute idle or on memory pressure. Pictures are saved as `kind = 'picture'` moments (file under `pictures/`), shown in the chat and timeline with a Report button (`src/features/ask/picture-report.ts`, an email draft).
- Recordings in the chat (`src/engine/speech-clip.ts`): a heard line's saved audio is shown with an answer only when the model picks the `play_recording` catalog tool ("let me hear that again"); other answers, even about what was said, show no clip (the timeline keeps them).

## Platform limits

**iOS:** no background camera; no custom wake word in the background (use side button voice-app setting, Back Tap, or the App Shortcuts in `app-intents/`: "Ask Sidekick", "Start voice question", "What am I looking at?" from Siri, Shortcuts, the Action Button or Control Center's Shortcut control; each opens the app, ADR 0006); background mic is allowed if started in the foreground (`audio` background mode, orange dot — App Review 2.5.4 / 2.5.14 need detailed review notes); no reading other apps' screens (share sheet, or a ReplayKit broadcast extension with a 50 MB cap); no notification / SMS / call-log access; no background GPU; no share-in (the chat's paperclip attaches files), text tools or "What did I miss?" yet; no speech from recordings or videos (their pictures are read) (ADR 6).

**Android:** camera / microphone foreground services must start while the app is visible; a mic FGS cannot start from `BOOT_COMPLETED` (Android 15+); the default-assistant role (Assist API) is the legitimate screen-context route; MediaProjection needs consent each session; AccessibilityService only for sideload builds; `MANAGE_EXTERNAL_STORAGE` is not allowed on Play → use SAF; native libraries must support 16 KB pages (targetSdk 35+).

Core features must work on both platforms; Android-only extras are optional.
